fix(ui): resolve the P5 namespace error CI caught and the local build missed

Two defects, one cause: I opened a `namespace Content {` inside the anonymous
namespace at AestraContent.cpp:91, so the descriptor struct and both table
functions landed in Aestra::(anon)::Content while every use site resolved
`Content::floatingPanelDescriptors()` against Aestra::Content, where nothing was
defined. An anonymous namespace has no name to qualify against — inside one you
refer to definitions directly, and I qualified anyway.

Dropped the wrapper. These definitions are file-local by construction, so the
anonymous namespace is the right home. The shared table stays qualified as
Content::kFloatingPanelGeometry, because that genuinely lives in Aestra::Content
and comes from the header.

Also updated the four FloatingPanelSpec call sites left behind by the rename.
Three pass a `view` parameter and the fourth passes ViewType::Sequencer directly,
so the argument is matched rather than assumed — the first attempt of that script
expected four identical lines, found three, and stopped instead of replacing what
it had. That is the behaviour that kept it from half-applying a rename.

THE VERIFICATION GAP, which is the part worth keeping.

This did not compile, and every local build I ran said it did. The reason:

  AESTRA_CI=ON force-sets AESTRA_HEADLESS_ONLY=ON, which sets
  AESTRA_ENABLE_UI=OFF.

Every local configuration this session passed -DAESTRA_CI=ON, following the
headless command in AGENTS.md. Headless does not compile Source/Core/, so
AestraContent.cpp was never built. **I verified a file I was not compiling.**

ci.yml is explicit about this at line 145: "Every other lane passes AESTRA_CI=ON,
which force-disables the UI, so without this job the app can silently stop
building (it did once for a week, #396)." There is exactly one lane that
compiles the app, and it is not the one AGENTS.md tells agents to run locally.

So the real defect was mine and it is not fixed by the namespace change: for any
work touching Source/Core/ or AestraUI/, the local command is wrong. Verified
both ways before pushing — headless for the suite, and a separate UI-on configure
building the Aestra target, which is what CI's failing lane does.

Suite 304/304. RT gate 35 TUs. Full UI/app build clean.
