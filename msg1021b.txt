fix(project-load): preserve a plugin's state when the plugin rejects it (#1014)

CodeRabbit found the real defect in my own fix. The first version reported a
plugin that rejected its own state and left the instance LIVE, running default
parameters. Reporting it was necessary and not sufficient: defaults sound
plausible, so the user would not notice, and the next save wrote those defaults
over the project's settings. The loss was not merely unreported -- it was
guaranteed on the first save.

A rejected state now takes the same path as a missing plugin. The slot ends up
empty and the opaque blob is preserved verbatim, so it is re-emitted unchanged
and the settings survive until the project is loaded again. The instance is
dropped with instance.reset() rather than activated.

Both branches also converged onto duplicated identity/mix assignment, so
instanceId, bypass, dryWet and faultState are now resolved once after the branch
instead of once per branch. A slot is an occupant either way.

What still differs is the diagnosis, which is why LoadReport keeps two lists
rather than one. "Install the plugin" and "this plugin could not read its state"
are different messages, and telling a user to install a plugin they already have
is its own kind of wrong. Neither list loses data now, but the recovery is
shared and the reason is not.

Two more CodeRabbit findings, both accepted:

- MuseProjectLoadReport used stateKind "plugin_instance" for the rejection
  entry, which would tell a consumer the user's plugin was absent. It is
  "plugin_state" now; the instance exists, its state is what would not load.
  The two existing stateKind values are audio_asset_content and plugin_instance,
  so this adds a third rather than misusing one.

- The new test returned EXIT_SUCCESS on both setup paths -- manager failed to
  initialize, or the EQ did not resolve -- with a SKIP message. That is a test
  that silently stops testing, which AGENTS.md §2 names directly. Both now
  return EXIT_FAILURE. The built-ins are always present in core mode, so a
  failure there is a real problem rather than an environment quirk.

Warning text in three places, the LoadResult doc, the LoadReport doc and the
JSON message all described the old live-on-defaults behaviour and were updated
to match. A warning that misdescribes the user's situation is worse than none.

Negative control, run against the NEW claim: removed instance.reset() to restore
live-on-defaults, and the test failed 5 assertions -- the slot is empty, the slot
holds a placeholder, the chain counts the placeholder, the state is preserved
byte-for-byte, and the plugin is reported. Restored and verified by content, not
by diffstat.
