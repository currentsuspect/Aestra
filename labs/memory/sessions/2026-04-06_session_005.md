## Key Findings (Research Only)

### Current Linux RT scheduling status:

1. **`RtAudioDriver::openStream()`** (line 105): Sets `RTAUDIO_MINIMIZE_LATENCY` only.
   Does **not** set `RTAUDIO_SCHEDULE_REALTIME`. Priority = 0.

2. **`RtAudioDriver::startStream()`** (line 170): Has `#ifdef __linux__` block that calls
   `pthread_setschedparam(pthread_self(), SCHED_FIFO, &param)`. The comment says
   "RtAudio creates its own thread; we set priority on the calling thread which should
   be the audio thread context at this point." **This is likely wrong** — `startStream()`
   is called from the UI thread, not the audio thread. The `pthread_self()` at this
   point is the UI thread, not RtAudio's internal callback thread.

3. **RtAudio internals**: When `RTAUDIO_SCHEDULE_REALTIME` flag is set, RtAudio uses
   `SCHED_RR` (round-robin) with `pthread_attr_setschedpolicy()` at thread creation time.
   This is the correct way — priority set via `pthread_attr` before `pthread_create()`.

4. **The ALSA backend in RtAudio**: Does NOT support `RTAUDIO_SCHEDULE_REALTIME` — only
   PulseAudio and JACK do. For ALSA, the `SCHED_RR` block is unreachable.

5. **`mlockall(MCL_CURRENT | MCL_FUTURE)`**: Called from `startStream()` on the UI thread.
   This DOES work — `mlockall` affects the entire process, not just the calling thread.
   So page faults are prevented globally.

### What's actually happening:

- **Scheduling**: `SCHED_OTHER` (normal CFS), NOT SCHED_FIFO or SCHED_RR
- **mlockall**: ✅ Working (process-wide, prevents page faults)
- **RtAudio callback thread**: Standard priority, no RT scheduling
- **The `pthread_setschedparam(pthread_self(), ...)` in `startStream()`**: Sets UI thread
  priority, not audio thread. This is a bug — the call has no effect on RT behavior.

### Fix would require:

- Pass `RTAUDIO_SCHEDULE_REALTIME` + non-zero priority to `openStream()`
- For ALSA: would need a custom thread creation path (RtAudio doesn't support it)
- Or: use a separate abstraction layer that creates its own `SCHED_FIFO` thread
  and calls into the audio callback from there

### Decision: **Not committing any change in this session.**
This is a bug fix, not a memory optimization. Belongs in a separate lab.
