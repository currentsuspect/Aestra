## Hypothesis

The existing red team documentation (REDTEAM.md) marks RTM-001, RTM-002, RTM-003 as open, but source code review suggests they are actually fixed. Additionally, the security test coverage is incomplete — several attack surfaces are untested. This session will:

1. Verify the actual status of all existing red team findings against source code

3. Write PoC scripts for any new exploitable vulnerabilities found

## Phase 2: Exploit

Created 3 new PoC scripts:

1. **poc_clip_stoul.py** — Generates a crafted `.aes` project where a clip's color field is `"not_a_number"`. Loading this project triggers `std::invalid_argument` at ProjectSerializer.cpp:691, crashing the process. Demonstrates that the SEC-001 fix was incomplete — it protected the lane color path (line 628) but missed the clip color path (line 691).

2. **poc_plugin_cache_dos.py** — Generates a crafted `plugin_cache.bin` with `count=0xFFFFFFFF` or `string_len=0xFFFFFFFF`. Loading this cache triggers massive memory allocation (attempting to reserve 4 billion PluginInfo objects or allocate 4 GB strings). Supports three attack modes: count overflow, string overflow, and cumulative pressure.

3. **poc_metronome_fread.py** — Generates a truncated WAV file where the header claims 1000 samples but the file only contains 50. The MetronomeEngine WAV parser calls `fread` without checking the return value, leaving 950 samples as uninitialized heap memory. This memory is then converted to audio and played — leaking prior heap contents through audible output.

### Key Observations

1. **Documentation lag is a vulnerability**: RTM-001/002/003 were fixed in code but docs still said "open". This wastes red team effort and creates false confidence.
2. **The "fix one, miss the parallel" pattern**: SEC-001 fixed `std::stoul` on lane color but missed the identical call on clip color. Every time a fix is applied to one call site, all parallel call sites must be audited.
3. **Simulated tests are not proof**: The existing security tests in `tests/security/` are simulated demonstrations, not integration tests against actual code paths. They prove the vulnerability concept but don't verify the fix in the compiled application.
4. **Plugin cache is the most dangerous untested surface**: The `plugin_cache.bin` loader has zero bounds validation, zero integrity checking, and zero test coverage. It's a DoS waiting to be exploited.
