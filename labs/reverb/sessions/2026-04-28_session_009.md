# Session 009 — 2026-04-28

## Objective

Investigate and optimize the LFO Normalize + Control path, identified in Session
008 as a ~7.4% stage. The target was `normalizeOscillator` which performs scalar
`std::sqrt` per LFO line, and `updateControlCache` which recomputes delay lengths
and gains.

## Starting State

- Branch: `develop`
- SHA: `b42e6e32` (Session 008)
- `kControlInterval = 32` — LFO normalization + control cache update every 32 samples
- `normalizeOscillator`: 16 scalar `std::sqrt` calls every 32 samples (8 lines × 2 oscillators)
- AVX2 path already uses `_mm256_rsqrt_ps` (fast approximate reciprocal sqrt)

## Investigation

### Attempt 1: Reduce Normalization Frequency from 32 to 64 Samples

**Hypothesis:** Halving the normalization frequency would reduce sqrt call rate by
50%, saving CPU time.

**Change:** Modified `kControlInterval` from 32 to 64.

**Benchmark results (5 iterations, 5s @ 48kHz, non-profile):**

| Mode | Interval 32 (Baseline) | Interval 64 | Delta |
|------|------------------------|-------------|-------|
| Room | 107,335 us | 109,577 us | +2.1% |
| Hall | 116,740 us | 112,041 us | -4.0% |
| Plate | 113,920 us | 102,249 us | -10.3% |

**Analysis:** The results are within the benchmark noise floor (~5-15% run-to-run
variance on the 2-core machine). No consistent improvement is visible. The Plate
result looks promising (-10.3%) but Hall is only -4.0% and Room is +2.1%. Without
consistent cross-mode improvement, this is indistinguishable from system noise.

**Why the improvement is too small to measure:**

The `normalizeOscillator` cost is:
- 16 sqrt calls every 32 samples
- At 48kHz: 48,000 / 32 × 16 = 24,000 sqrt calls/second
- `std::sqrt` on modern x86: ~10-20 cycles
- Total: 24,000 × 20 = 480,000 cycles/second
- On a 2GHz core: ~0.24% of one core

The 2-core machine's benchmark variance is ~5-15%. A 0.24% improvement is
completely buried in noise.

### Attempt 2: Investigate Reciprocal Sqrt for Scalar Path

**Hypothesis:** Replace `1.0f / std::sqrt(mag2)` with a fast approximate rsqrt.

**Analysis:**
- The AVX2 path already uses `_mm256_rsqrt_ps` (hardware approximate rsqrt)
- A scalar fast rsqrt (e.g., `__builtin_ia32_rsqrtss` or Newton-Raphson) would
  save ~10-15 cycles per call
- Total savings: 24,000 × 15 = 360,000 cycles/second = ~0.18% of one core
- Still far below the measurement threshold

**Decision:** Not attempted. The expected gain (~0.2%) is smaller than the
benchmark noise floor (~5-15%). Adding approximate math for unmeasurable gain
violates the principle of simplicity.

### Attempt 3: Investigate Control Cache Update Cost

The `kLFOControl` profile stage includes BOTH normalization AND `updateControlCache`.
The control cache recomputes:
- 8 FDN line lengths
- 8 feedback gains
- 4 diffuser lengths
- 12 early reflection delays and gains
- LFO phase increments

This is non-trivial work, but it only happens every 32 samples. At 48kHz, that's
1,500 updates/second. Each update involves ~50-100 arithmetic operations. Total
cost: ~150,000 ops/second = negligible on modern CPUs.

## Conclusion

**LFO Normalize + Control is NOT a reliable optimization target on this machine.**

The stage appears large (~7.4%) in the profile build, but:
1. Profile builds run ~2.5x slower than production builds, inflating the relative
   cost of infrequent operations
2. The actual production cost is <1% of total CPU time
3. The benchmark machine's run-to-run variance (~5-15%) swamps any potential gain
4. The AVX2 path is already optimally vectorized with `_mm256_rsqrt_ps`

## Honest Assessment

The LFO Normalize + Control stage is a profiling artifact, not a real production
bottleneck. In profile builds, the 18 `std::chrono` calls per sample (2 per stage
× 9 stages) dominate the overhead. The infrequent LFO normalization appears large
relative to the profiled total, but in production it is <1% of CPU time.

This is a classic example of **profiler distortion**: compile-time instrumentation
with `std::chrono` adds constant overhead per sample, which makes infrequent
operations appear proportionally larger than they are in production.

## Recommended Session 010 Target

**Parameter Smoothing** — currently ~4.4% in profile builds.

The parameter smoothing runs every 4 samples (`kSmoothBlock = 4`):
```cpp
if (smoothCountdown == 0) {
    for (uint32_t p = 0; p < kParamCount; ++p) {
        if (p == kBypass || p == kMode) continue;
        const float target = m_params[p].load(std::memory_order_relaxed);
        smoothedParams[p] += (target - smoothedParams[p]) * blockSmoothingCoeff;
    }
    smoothCountdown = kSmoothBlock;
}
```

This is 9 parameter smooths every 4 samples = 2,250 smooths per sample at 48kHz.
Each smooth is a subtract + multiply + add = 3 FMAs. Total: ~6,750 FMAs/second.
This is also likely too small to measure, but it could be vectorized as a 4-wide
SSE loop for the 9 parameters (process 4 at a time, then the remainder).

**Alternative target:** The `Output/Mix` stage (~14.0%) includes the width matrix:
```cpp
const float widthL = wetL * control.widthMain + wetR * control.widthCross;
const float widthR = wetR * control.widthMain + wetL * control.widthCross;
```

This is 4 FMAs per sample that could be vectorized as a 2-wide dot product on
SSE. However, the scalar version is already only ~4 FMAs, so the win would be
minimal (2 SIMD ops vs 4 scalar ops).

**Most honest recommendation:** The remaining hotspots (FDN Delay Read at ~28.6%,
Output/Mix at ~14.0%) are fundamentally limited by:
1. Cubic Hermite interpolation arithmetic (64 FMAs per sample)
2. Memory bandwidth (32 float reads per sample from 8 delay lines)
3. Output width matrix (4 FMAs per sample)

These are not easily optimizable without:
- Changing interpolation order (violates hard constraint)
- Major SIMD restructuring of delay-line memory layout (topology change)
- Accepting approximate math (not justified by measurable gains)

The reverb has reached a **performance plateau** with the current architecture.
Further meaningful gains would require:
- An AVX2-capable machine (projected 1.5-2.0x speedup from AVX2 FDN path)
- A machine with more stable benchmarking (to measure sub-5% optimizations)
- A redesign of the FDN delay-line memory layout for gather-friendly access
