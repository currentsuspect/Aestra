# Session 002 — 2026-04-06 (early afternoon)

## Summary

Second session. Fixed the RT scheduling bug — moved priority setup from
`startStream()` (UI thread) to `rtAudioCallback()` via `pthread_once` (actual
RtAudio callback thread).

## Rounds

| Round | Hypothesis | Result | Notes |
|-------|-----------|--------|-------|
| 02 | Set SCHED_FIFO from callback via pthread_once | ✅ accept | All hard gates pass. Fix runs on correct thread. Graceful degradation without CAP_SYS_NICE. |

## What Changed

**Before (broken):**
```cpp
// startStream() — called from UI thread
pthread_setschedparam(pthread_self(), SCHED_FIFO, &param); // WRONG THREAD
mlockall(MCL_CURRENT | MCL_FUTURE); // Actually works (process-wide)
```

**After (fixed):**
```cpp
// rtAudioCallback() — called from RtAudio's internal callback thread
pthread_once(&s_rtOnce, &setupRealtimeScheduling); // CORRECT THREAD
// setupRealtimeScheduling() calls sched_setscheduler + mlockall
```

## Key Findings

1. **`pthread_once` runs on the callback thread** — The first time the callback
   fires, `pthread_once` executes `setupRealtimeScheduling()` on the actual
   RtAudio thread. This is the correct thread to set scheduling on.

2. **`pthread_once` is RT-safe** — It uses atomic operations internally. After
   the first call, subsequent calls are essentially a single atomic load.

3. **`mlockall` is process-wide** — Works regardless of which thread calls it.
   Calling it from the callback is fine.

4. **Without CAP_SYS_NICE, sched_setscheduler fails silently** — This is correct
   behavior. In CI/container environments, the audio thread will run SCHED_OTHER
   but the app still works. No crash, no error.

5. **The old code in `startStream()` was dead code** — `pthread_self()` returns
   the UI thread ID. Setting priority on the UI thread has no effect on the
   RtAudio callback thread. The fix removes this dead code entirely.
