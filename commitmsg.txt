fix(project-load): report a plugin that rejects its own state (#1014)

EffectChain::loadState had two failure modes that looked identical from the
outside and were not the same event:

  not installed         createInstanceById returns null. The slot keeps the
                        opaque record verbatim and re-emits it on save. Nothing
                        is lost; only this machine is short a plugin. Already
                        reported, as missingPlugins (#647).

  installed, state bad  The slot goes LIVE, running DEFAULT parameters. The
                        settings in the project were not applied, and the next
                        save overwrites them. The project is damaged.

The second case only reached Aestra::Log::warning, and the return value still
meant "the blob parsed". The project opened cleanly, every caller saw success,
and nothing anywhere said the user's settings were gone. Silent data loss with a
log line standing next to it.

The two are now separate lists on a LoadReport struct, because one out-param
could not express both and collapsing them was the original defect. A struct
rather than a second std::vector<std::string>* so the two cannot be swapped at a
call site -- they are the same type, which is exactly the hazard.

loadState's return value is deliberately unchanged: a plugin's own rejection is
not a chain parse failure, and folding it in would make every caller report a
corrupt project because one plugin was unhappy.

Surfaced at all three ProjectSerializer call sites (mixer channel, Master strip,
lane), in ProjectSerializer::LoadResult::unreadablePluginState, and in the
MuseProjectLoadReport JSON as issueCode "plugin_state_rejected" with
placeholderPreserved=false. isDegraded() now counts it: a plugin running
defaults is a degraded load even though the blob parsed cleanly.

Testing: new EffectChainUnreadablePluginStateTest, 302/302 suite.

The new test uses a REAL built-in plugin, because the whole point is the
installed-but-rejecting branch -- an unresolvable id takes the placeholder path
and would make the test pass for the wrong reason. That is the mirror of
EffectChainMissingPluginTest, which depends on NO plugin resolving so it can
drive the placeholder path. Neither can substitute for the other, and the new
test says so in its skip message rather than reporting SKIP as a pass.

It pins the consequence rather than describing it: the rejected bytes are NOT
what gets written back, because the live slot re-emits the plugin's own state.
A control case asserts a valid state reports nothing and round-trips
byte-identically, so the two are shown to differ in exactly the way the report
claims.

Negative control: removed the outReport->unreadableState.push_back and the new
test failed with "[FAIL] the rejected plugin is reported", exit 1. Restored,
verified by explicit grep for the marker rather than by diffstat, after #1018
taught me what a stale sabotage looks like.

Four existing EffectChain tests were migrated to the new out-param type.
